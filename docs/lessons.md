# 踩坑回顾与设计经验（v0.1 → v0.5）

> 2026-09-17 · 从一个"只响一声"的 v0.1 空壳到可发布的 v0.5.0，把这一路踩过的坑和沉淀的设计原则集中记录，供后续维护者（包括未来的自己和 AI 协作者）参考。证据级细节见 docs/research/01~08、docs/adr/0001~0006、docs/report-v0.2~v0.4。

## 一、产品级踩坑：为什么 v0.1 "效果不佳"

教训的起点不是参数，而是**核心链路根本没有闭环**：

1. **"最后一公里"没有验收就当作完成**。系统通知是 `log::info!` 占位、护眼 25 秒没有任何载体、全局热键从未注册——spec 写了、任务清单打了勾、`#[allow(dead_code)]` 把编译器告警也压住了，但用户视角里这些功能不存在。
   → 对策：v0.2 起，每个功能按"用户能看到/听到什么"验收；不允许用 allow 压死代码告警来粉饰。
2. **上下文感知把"提醒"变成了"消失"**：心流和游戏状态下，到点的提醒被空分支吞掉还顺手重置计时器——越专注的人越收不到提醒，与产品目标完全相反。
   → 对策：ADR-0002 确立"上下文只能改变投递时机与形态，不能取消提醒"，并有 12 个调度核心单测锁住该规则。
3. **单信号判定不可靠**：只用键盘判"离开"（鼠标用户被误判）、只用窗口尺寸判"全屏"（自动隐藏任务栏误判）、只用 QUNS 判"不可打扰"（本机长期谎报 D3D 独占）。
   → 对策：多信号交叉佐证（QUNS 忙碌类 + 矩形佐证 + 输入空闲），且**必须排除自己进程的窗口**——我们自己的全屏边缘渐暗层会触发全屏检测，把自己误判成游戏。
4. **默认值拍脑袋**：心流阈值 10 键/30 秒 = 0.33 键/秒（任何打字都算心流）；间隔 10~18 分钟无出处。
   → 对策：ADR-0001 用 AOA 指南 + RCT 重新锚定默认值；伪需求（蓝光过滤、强制锁定）有 Cochrane/AAO 背书后才敢"不做"。
5. **环境差异是隐藏放大器**：同一份代码，在本机因 QUNS 长期谎报 D3D 独占，视觉提醒被永久静音——"效果不佳"在特定机器上被环境放大数倍。
   → 对策：可打扰性判定加矩形佐证；日志落在 `%APPDATA%\eyeflow\eyeflow.log`，出问题先看日志。
6. **状态机与真实使用节奏的边界**：看视频不动鼠标 3 分钟被判"离开"（与 Stretchly/LookAway 一致的有意取舍）；睡眠时间被 Windows 计时算进 dt，开盖瞬间轰炸预告。
   → 对策：离开=计时暂停 + 进入即记自然休息；dt > 10 分钟按离席归来处理。

## 二、架构级经验

### 2.1 后台工具的内存模型："无窗口时零 GUI"

最初 v0.2 试图常驻 eframe，实测在 NVIDIA 机器上一个空窗口就占 163 MB 私有内存、常驻 203 MB——与被用户诟病的 Electron 同量级。最终改为**轻量循环（无窗口、无 GL）⇄ 按需 eframe 会话**：空闲 16 MB，只在显示浮窗/设置时短暂进入 UI 会话（ADR-0006）。

经验：
- **先测再定架构**。"数十 MB"的假设被一台机器实测推翻；桌面 GUI 框架的常驻成本大头是 GPU 驱动，不是你的代码。
- eframe 的 `run_and_return` 支持同线程反复进出事件循环，这是"按需会话"得以成立的关键。
- 常驻托盘/热键必须在运行 Win32 消息泵的线程上创建；轻量循环用 `PeekMessageW`、会话期由 winit 泵，两模式共用同一份 `Runtime::step`，**保证窗口开不开、功能都不停摆**。

### 2.2 并发与事件：单一泵 + 事件总线

键盘钩子线程（自带 GetMessage 泵）、传感器线程（1 Hz）、托盘/热键（全局 channel 轮询）全部通过事件总线进入主线程；UI 会话期额外用全局 `egui::Context` 句柄唤醒。**同一条 `Runtime::step` 在两种模式下执行**，杜绝"开设置窗就冻结一切"的 v0.1 缺陷。

### 2.3 UI 宿主的视口细节（egui 0.36 + winit 0.30）

> 追记（v0.5.2）：预告期“边缘渐暗”先后经历两种实现（分层 GL 视口窗 → 闪烁；原生静态窗 → 无闪烁但用户反馈影响性能），最终**整个功能被移除**。教训：四条全屏宽度的合成层窗口（即便是静态的）在桌面合成器里仍产生可见的合成开销与视觉干扰，“余光可感”的收益抵不过用户对性能/干扰的感知——预告浮窗本身已经足够。

- 子视口一帧不被 `show_viewport_immediate` 使用即被销毁——浮窗每次出现换新 `ViewportId` 重建，正好绕过 **winit 的 `with_active(false)` 只在首次显示生效**（再次 `set_visible(true)` 会抢焦点）的坑；再补 `WS_EX_NOACTIVATE` 保证点击也不夺焦。
- 根视口是一个屏幕外 1×1 锚点：eframe 在根不可见时只跑 `logic` 不跑 egui pass，子视口必须靠"根可见或后代可见"才能渲染。
- glow 清屏色不透明——**全屏透明视口整片黑**。预告期"边缘渐暗"因此改用 4 条细边窗 + 整窗 `LWA_ALPHA` 半透明（点击穿透 + 不激活）。
- 屏幕外锚点在 Windows 上稳定（-26214 与系统最小化位姿同源），但要注意多显示器负坐标区的 DPI 取值。

### 2.4 检测层：平台 API 要怀疑

- `SHQueryUserNotificationState` 是官方"能否打扰"API，但 `RUNNING_D3D_FULL_SCREEN` 存在长期谎报；`SetForegroundWindow` 有前台锁；`with_active(false)` 只管首次显示；`GetSystemMetrics`/`MonitorFromWindow` 在混合 DPI 下要分清逻辑/物理像素。
- 键盘钩子（WH_KEYBOARD_LL）要过滤自动重复（低级钩子没有 KF_REPEAT，需自维护按下状态）和修饰键；回调只发时间戳立即返回。
- Win32 计时**包含睡眠时间**：跨睡眠的 dt 会灌爆计时器与用屏累计。

### 2.5 音频与通知

- rodio 的 `Mixer::add` 自动重采样到设备采样率（查源码确认，v0.1 审计里的"变调"担忧不成立）；`Decoder` 流式播放用户音频，不整包载入内存；无设备降级为静音，绝不 panic。
- 自绘通知界面按微软要求必须查询 `SHQueryUserNotificationState`；气球通知（NIF_INFO）未弃用但 TrayIcon 无法复用其 HWND，WinRT Toast 需 AUMID+开始菜单快捷方式——v0.5 选择自绘浮窗作为主视觉通道即源于此。

## 三、工程与流程经验

1. **配置即契约**：serde 全字段 `#[serde(default)]` + `sanitized()` 夹紧 + 解析失败改名备份 + v0.1 迁移保留用户自定义——旧配置永远不被静默销毁。
2. **纯逻辑核心可测**：`core.rs` 不碰 Win32/egui，时间由调用方注入，49 个测试锁住调度规则；v0.4→v0.5 的每次改动（长休息延后、睡眠阈值）都是改规则→改测试→全绿的循环。统计落盘用脏标记，测试不污染真实数据。
3. **CI 要从第一天就上**：edgedim 的测试断言在 GNU（本地）能推断通过、在 MSVC（CI）报错——本地绿 CI 红的工具链差异，靠"CI 从第一次提交就在"来兜底，而不是事后补。修复方式：断言用显式 `egui::vec2` 而非依赖推断。
4. **CI 环境≠本地环境**：choco 装 NSIS 后任务内 PATH 不刷新（用绝对路径调用）；日志下载接口未授权时 403（失败排查要靠 `gh run view --log-failed`，前提是已 `gh auth login`）。
5. **批处理脚本不要写中文**：UTF-8 中文 .cmd 在代码页切换完成前就被解析器拆碎，报一堆乱码命令。面向用户的脚本用 ASCII。
6. **依赖取舍要有依据**：rodio 裁掉解码器省 2 MB，后来为自定义音频再加回（需求变了就改）；rdev/single-instance 停更不引入；UPX 因杀软误报不用。
7. **仓库卫生**：649 MB 里 99.8% 是构建缓存——迁移按白名单复制；exe/安装包一律走 CI 产物，不进仓库。
8. **文档即决策**：CONTEXT.md（词汇表，统一"顺延/延后"等用语）、ADR（每个不可逆决策附来源 URL）、research/（六份带引用的调研）——事后排查和交接都从这里起步。

## 三点五、i18n 与字体（v0.6 追记）

1. **字形覆盖必须实测 cmap，不能靠"这个字体是中文字体所以应该有"**。v0.6 的 i18n
   开工前查了一轮字体覆盖率,结论是：`✓`(U+2713) 与 `▶`(U+25B6) 在
   `msyh.ttc` / `msyhl.ttc` / `simhei.ttf` **全部没有 glyph**，而这两字符出现在
   「已保存 ✓」「▶ 试听」两处界面上——**v0.5.2 的中文界面今天就在显示豆腐块**，
   而且已经发版五个版本了。egui 没有系统级字体回退，缺字就是方块。
   修法是把 `seguisym.ttf` 注册为两条字体链的**尾部回退**（它有 `✓ ▶ ● · × 👀 👏` 全套）。
   **教训的形状**：字体链的"候选"不是"随便挑一个能读的"——每个字符都要能被链上
   **某一个**字体画出来才算覆盖，否则你挑中的那个恰好缺这一类符号。
   诊断手段见 `tests/i18n_glyphs.rs` 的 `probe_coverage`（打印 7 个危险字符 × 每个候选字体的覆盖矩阵）。

2. **别把"零分配"写成空话**。`tr(key) -> &str` 的无参路径确实零分配：一次
   `AtomicU8` 读取 + 一次二分查找，返回指向静态表里字符串字面量的引用。但带参路径
   `tr_fill` / `trn` 是 `str::replace`，**必然一次 `String` 分配**。把两者笼统写成
   "i18n 层零分配"会让下一个读代码的人按错误的模型做判断（比如试图把 `SettingsAction`
   里的 `String` 换成 `&'static`）。诚实的写法是**逐路径标注**，并在模块注释里说明
   为什么带参路径的分配可以接受（那些调用点本来就在 clone 整个 `Config`）。

3. **DTD 式的"键集合守门人"要放在构建期，而不是测试期**。`build.rs` 用
   `str::lines()` 解析 `locales/*.toml`（**故意不加 `toml` 这个 build-dependency**——
   为解析两个自己写的文件重复编译整个 toml crate 树不成比例），任一语言缺键或多键直接
   `panic!` 让构建失败。这才是本项目 i18n 唯一差异化的能力：现成的 Fluent / rust-i18n /
   i18n-embed 都只会在**运行时**漏 key，而运行时漏 key 的表现是界面上原样显示
   `tray.open_settings`。

4. **扁平 locale 表的键必须加引号**。`tray.open_settings = "打开设置"` 里的点是
   **TOML 的嵌套表分隔符**——真正的 TOML 解析器会把它读成 `[tray]` 下的
   `open_settings`，于是"扁平表"变成嵌套表，任何按 `toml::Table` 逐条取
   `as_str()` 的代码都会拿到一个 Table 而不是 String。写成
   `"tray.open_settings" = "打开设置"`（带引号的**字面量键**）才既保留点分又保持扁平。
   这是"我们的格式是自定的扁平格式"与"别人也会拿真的 TOML 解析器读它"之间的冲突点。

5. **把枚举的 `label()` 搬进数据层，测试才不会被语言状态污染**。若
   `FlowSensitivity::label()` 内部读 `AtomicU8` 语言状态，`config.rs` 的 10 个测试与
   `core.rs` 的 14 个测试就变成**顺序相关**：一个把语言设成 `EnUs` 的测试会污染同进程
   后续所有测试。改成「枚举只给出 locale 的 key，文案由调用点 `tr()` 现取」之后，
   `config.rs` / `core.rs` 保持纯数据、零测试污染，加第三种语言时也永不触碰领域层。

6. **「上游没有 X 字段」推不出「用了 X 的那个 API 是空操作」**。v0.6 写下过一句
   「`RichText::strong()` 在中英文下都是空操作」，依据是 `epaint` 的 `FontId` 里
   没有 `FontWeight` 字段。**这是错的**：`strong()` 改的是**颜色**（`widget_text.rs:484-485`
   → `style.rs:1146` → dark 主题下纯白 255 对灰 140），标题层级一直成立，v0.6.1 才由
   源码推翻。**教训的形状**：查一个 builder 方法的行为，要读**它自己的实现**，
   不是读它依赖的数据结构。字重那条结论（`FontWeight` 确实 0 次）是对的，
   但它只否证了「字重」，没否证「`strong()`」。**一个正确的上游事实被外推成了一个
   错误的 API 判断**——而且这个错误还从 ADR 扩散进了 `src/app.rs` 的生产注释。
   **ADR 里的断言会被抄进代码注释，所以断言错了会跟着活很久。**

7. **一个「省内存」建议必须先回答「省的是哪一块」**。v0.6.1 一轮里，三个看起来都对的
   优化建议全被否掉，因为它们都在优化一个**从没被测量证明是大头**的量：
   「给 `max_texture_side` 设上限」（上游已在 `fonts.rs:981` 用 `at_most(16*1024)` 夹住，
   实测图集只有 2~8 MB，压到 2048 反而多触发整图 clone，**净负**）；
   「追 1 MB/会话漂移」（落在消融噪声带内）；
   「42 MiB 字体链就是 52 MB 残渣」（同一轮的语言对比实验把它直接证伪：换掉 38.6 MB
   字体，残渣只动了 2.24 MB）。**唯一通过同一把尺子的那个——砍掉两个对文案贡献
   **0 个字符**的字体（fontTools 逐个 cmap 实测）——确实有收益。**

8. **两次消融的比值差一个数量级，就该先怀疑噪声**。去掉 `seguisym` 移掉 2.51 MB 字体、
   残渣「降」3.16 MB（比值 1.26×）；语言对比移掉 38.6 MB 字体、残渣只「降」2.24 MB
   （比值 0.058×）。**相差 22 倍，不可能存在一致的传递函数**——那 ±3 MB 的差就是
   消融的重复性噪声。**先怀疑自己的尺子，比急着建立解释便宜得多。**

9. **内存采样必须等落定，工作集不是能还的东西**。残渣要 **~12 秒**才从 102 MB 落到
   56 MB，不等落定就采样会系统性高估斜率；而 `SetProcessWorkingSetSize(-1,-1)`
   能把工作集压掉 92% 而**私有字节一动不动**——**工作集不是 commit charge，
   私有字节才是**。「裁剪后掉了 92%」绝不能写成「泄漏修好了」。

10. **字体链的字面量副本会让测试失去牙齿**。`tests/i18n_glyphs.rs:25` 的 `ZH_FONTS`
    是一份**手抄字面量**，不从 `src/app.rs` 解析；T11d 用 `src.contains("msyh.ttc")`
    扫源码全文，**注释里出现这个字符串就算过**（实测 `segoeuib.ttf` 早已从 `EN_FONTS`
    移除，T11d 仍绿，因为它命中的是注释）。于是砍字体链之后全套测试仍然全绿——
    **测试不会替你抓住回归**。凡是「代码里有一份、测试里又抄了一份」的东西，
    就要有一条断言把两者绑死，否则第二份会静默腐烂。

11. **作者自己不用，是最真实的一手用户研究数据**。`config.rs:142` 的出厂默认是
    `enabled = true`，而作者在**自己的** `%APPDATA%\eyeflow\config.toml` 里手改成了
    `false`，短休息 44 秒、音量 120%、提示音 3 秒、免打扰禁用。**这套配置比任何
    可用性问卷都诚实**：它说明这个工具对它的作者来说太吵了。
    **但记下它不等于要改它。** `PROJECT_STATE.md` §3 已明文「是用户自己的选择，
    勿顺手修复」；而且「护眼工具催用户使用护眼工具」是最反直觉的产品设计，
    直接违反 ADR-0003 的 gentle by default。**结论：写进 lessons（知识），
    不写进代码、不加任何 nag（行为）。** 知识与行为在这里必须分开。

12. **双语化验收只验了「字画得出来」，没验「排得下去」——这是两件事**。v0.6 引入
    en-US 之后，验收清单里有字形覆盖（`tests/i18n_glyphs.rs` 扫 cmap）、也有英文界面
    目视截图，**唯独没有一条「每条界面文案在默认窗口宽度下不越界」**。后果是英文
    界面在 700 物理像素（= 560 逻辑 = 546 pt 内容区）下整片截断，而中文侧一条都
    不过界——**因为中文 31 字 ≈ 英文 101 字符，这个缺陷在验收当天就是隐形的**。
    更糟的是它对「滚动三帧截图」免疫：三轮恰好都停在设置窗上半部分，出问题的卡片
    在下一屏。
    **根因不是「egui 的 label 不换行」**——实测 `Ui::wrap_mode()`
    （`egui-0.36.1/src/ui.rs:588-604`）在**竖直布局下返回 `TextWrapMode::Wrap`**，
    `ui.label` / `ui.weak` / `ui.checkbox` 都会换行（本项目 `ui.weak_interval_random`
    就在那张截图里折成了两行）。真正会越界的是 `ui.horizontal`：`Layout::left_to_right`
    的 `main_wrap` 是 `false`（`layout.rs:141-152`），于是 wrap_mode = `Extend`，
    galley 的 `max_width` 被设成 `f32::INFINITY`（`label.rs:229-236`），
    **画到卡片边框外面，只被 ScrollArea 裁掉**。
    **教训的形状**：**每加一种语言，都要有一条按该语言实测的宽度验收，而不是靠
    「截图看着没问题」**；断言的对象应当是**不变量**（默认内容区 546 pt，任何内联
    标签的 `layout_no_wrap` 宽度都必须 ≤ 它），不是「肉眼看一眼」。另外 v0.6.1 把
    `spacing.slider_width` 从 100 抬到 220（`src/app.rs:502`）**顺手造出了同一类缺陷
    的新实例**：一行两个滑条从 510 pt 涨到 750 pt，直接冲出 546 pt——**「改一个
    spacing 常量」和「改文案」一样，都是排版改动，都得重跑宽度验收**。

13. **宽度闸门的测量台必须复刻控件「所在的那个布局」，否则它量的是一个不存在的
    场景**。`tests/layout_width.rs`（v0.6.1 新增）把每处内联文案统一塞进一个
    `ui.horizontal`（`TextWrapMode::Extend`，`max_width = f32::INFINITY`）再量宽度，
    于是 4 处**竖直布局里**的文案被判超宽。实测反证：`.shots/settings-en.png` 里
    `ui.weak_interval_random`（英文实测 618.2 pt）**折成两行、完整显示在卡片内**。
    机制与第 12 条同源：`Ui::wrap_mode()`（`egui-0.36.1/src/ui.rs:588-604`）在竖直
    布局返回 `Wrap`，`ui.label`/`ui.weak` 走 `label.rs:229-236` 折行；**`ui.checkbox`
    也一样**——`Checkbox` 内部是 `AtomLayout`（`checkbox.rs:96-100`），非 `Extend`
    时它给文本 atom 打 `shrink`（`atom_layout.rs:282-295`），于是照样折行。
    「checkbox 会越界」是错的。
    **教训的形状**：**断言的强度不得超过它在真实上下文里的后果**；按控件种类开
    豁免（"`ui.weak` 折行所以不管"）尤其危险——本项目 `src/ui.rs:720` / `:822` 的
    `ui.weak` **就在 `ui.horizontal` 里**（真会越界），一刀切豁免会把它们一起放过。
    正确的豁免单位是**布局上下文**：只有处在 `Extend` 布局（`ui.horizontal` /
    `horizontal_top` / `horizontal_centered`）里的控件才可能越界。

## 四、仍然有效的已知限制（截至 v0.5.0）

- 浮窗/严格遮罩只覆盖主显示器；多显示器在 Roadmap。
- "欢迎回来"闪屏的视觉样式未经人工截图确认（逻辑与计时已有单测）。
- 会话结束后显卡驱动残留：v0.5.2 记录为「~60 MB 私有内存」，v0.6 重新实测为**关闭设置窗后 55.14 MB 私有 / 81.07 MB 工作集**，长开实例（24.8 小时）为 77.41 MB 私有——与旧记录同量级，未变坏也未变好。**v0.6.1 已把这个现象拆到成分一级**（完整实测见 [ADR-0006 实测附录二](adr/0006-eframe-on-demand-ui-session.md)）：残渣的 **71%（46.70 MB）是首次建窗时一次性付清的驱动初始化**（进程模块数 39 → 85 → 76 后恒定），此后每次开关窗只漂移约 0.66 MB 且已判定为消融噪声；**工作集裁剪能把工作集压掉 92% 而私有字节一动不动**，所以它既不是堆碎片也不是高水位，**用户态拿不回**。彻底解决需浮窗 Win32 自绘，见 Roadmap。
- **默认关闭的功能也要算体积**：`ureq` 用默认 features，把 `rustls` + `ring` + `webpki-roots` 无条件拖进二进制，而 `update_check_enabled` 默认 `false`（`update.rs` 模块注释自己写着"可选"）。评审时拒绝了体积 5~8% 的 i18n 依赖，却没检查自己 `Cargo.toml` 里一个 400 KB 量级的默认关闭依赖——**审查依赖清单时，"默认 features"和"默认关闭的开关"要一起看**。
- **`panic = "abort"` 不让 panic hook 变死代码**：它只取消 unwind，hook 仍由 panic runtime 在 abort 之前调用。反倒是无控制台的托盘程序只往日志文件写 panic，崩溃时用户界面上什么也看不到——`set_hook` 里必须弹 `MessageBoxW`。
- 完整电源/锁屏事件桥（WM_POWERBROADCAST / WTS 通知）未做，>10 分钟睡眠用 dt 阈值兜底。
- exe 未签名，首装有 SmartScreen 提示。
