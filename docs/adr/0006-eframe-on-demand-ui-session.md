# UI 宿主采用按需启动的 eframe 会话（隐藏锚点根视口 + 子视口），空闲时不持有任何 GL 上下文

v0.1 在主循环里按需调用 `eframe::run_native` 打开设置窗，但核心逻辑不在 eframe 内运行，`run_native` 一阻塞，托盘、提醒、状态机全部停摆；主线程还跑着一个自写的 `PeekMessageW` 泵与 winit 抢消息。最初的 v0.2 方案是让 eframe（0.36，glow）常驻，根视口隐藏、逻辑在 `App::logic` 中按 1 Hz 推进。**实测推翻了它**：在 NVIDIA 显卡的 Windows 机器上，一个什么都不画的空 eframe 窗口就占 163 MB 私有内存（GL 上下文 + 驱动堆），EyeFlow 常驻达 203 MB——与被用户诟病的 Electron 竞品同一量级，直接摧毁“Rust 轻量”这个差异化卖点。

最终方案：
- 主线程平时跑一个**轻量循环**（`PeekMessageW` 泵 + 200 ms 轮询），没有任何窗口和 GL 上下文；托盘（tray-icon）、全局热键（global-hotkey）在启动时于主线程创建，两种模式下都能收到消息。
- 只有当需要显示窗口（预告浮窗 / 休息面板 / 设置窗）时才调用 `eframe::run_native`，进入 **UI 会话**；eframe 的 `run_and_return`（默认开启）把 winit 事件循环缓存在线程局部变量里并用 `run_app_on_demand` 运行，因此可以在同一线程反复进入、退出。
- 会话期间根视口是一个 1×1、放在屏幕外的锚点窗口，只为让 egui pass 每帧运行；三种窗口都是子视口。浮窗每次出现都换新的 `ViewportId`（新的原生窗口），因为 winit 只在窗口**首次**显示时尊重 `with_active(false)`；再叠加 `WS_EX_NOACTIVATE`，做到“看得见、点得动、不抢焦点”。
- 所有窗口关闭后会话结束，GL 上下文释放，回到轻量循环。
- 核心逻辑（`Runtime::step`）在两种模式下调用同一份代码，因此无论窗口开不开，提醒计时、托盘与热键都不会停摆。

## 实测（Windows 11，NVIDIA 独显，2026-09-08）

| 状态 | 工作集 | 私有内存 |
|---|---|---|
| 空闲，从未打开过窗口 | 15.6 MB | 2.5 MB |
| UI 会话期间（休息面板 + 设置窗） | ~175 MB | ~200 MB |
| 会话结束后空闲（驱动堆残留） | ~87 MB | ~60 MB |

spec N1 维持“<30 MB 常驻（未打开窗口时）”，并如实标注会话后的残留。

## 实测附录二：残渣的成分（2026-09-26，v0.6.1）

**这份附录回答一个问题：关窗之后剩下的那几十 MB 到底是什么，能不能拿回来。** README 与本 ADR 都引用过这个现象，本次第一次把它拆解到成分一级。

| 实验 | 数字 | 读法 |
|---|---|---|
| 开关设置窗 20 次（中文） | 3.03 → 49.73（第 1 次）→ ~58（第 2–15）→ 69.19（第 20 次）MB | 残渣 **71%（46.70 MB）一次性**到位；此后约 0.66 MB/会话 |
| **工作集裁剪** `SetProcessWorkingSetSize(-1, -1)` | 工作集 38.19 → **3.22 MB（−92%）**；私有字节 60.21 → **60.21（+0.002）** | **决定性的一条** |
| 语言对比 en vs zh | 残渣只差 **2.24 MB**（71.43 vs 69.19，3.4%）；会话内峰值差 **74.2 MB** | CJK 字体**只占峰值，几乎不占残渣** |
| 消融 | 关设置窗 UI 渲染：−7.15~9.44 MB；关**严格模式 + 壁纸：精确 0**；关 `seguisym`：−3.16 MB | 残渣主体是 **GL 上下文 + egui 基建** |
| **进程模块数** | 39（空闲）→ 85（会话中）→ **76，此后永远 76** | NVIDIA GL 驱动栈**一次性映射并永久驻留** |
| 残渣落定 | 102 → 78 → 56 MB，需 **~12 秒** | **采样必须等落定** |

**四个结论，每条都直接约束本 ADR 的架构选择：**

1. **不是堆碎片，也不是高水位。** 工作集裁剪能把工作集压掉 92%，而私有字节一动不动——如果残渣是「堆里的空闲块」，裁剪工作集本该同时降低 commit charge。**没有降低，说明它是真实被提交（committed）的页。** 高水位假说同样被排除：高水位意味着后续分配会复用这些页，`fs::read` 一个 19 MB 字体的瞬时峰值本该被残渣吸收，而实测残渣与是否读过 CJK 字体几乎无关。

2. **是驱动的 commit，用户态拿不回。** 模块数 39 → 85 → 76 且此后恒定：NVIDIA 的 OpenGL 驱动在首次创建上下文时一次性映射了一整套 DLL，进程不退出就不释放。**Rust 侧没有任何 API 能把这部分还回去**——它不属于我们的分配器。

3. **字体不是残渣的主因。** 把 38.6 MB 的 CJK 字体整个换掉，残渣只动了 2.24 MB。**这一条推翻了本项目内部长期存在的直觉**（见 [ADR-0007 推翻 4](0007-v0.6-scope.md)）。

4. **消融的两次比值相差 22 倍，所以 ~0.66 MB/会话是噪声。** 去掉 `seguisym`（移掉 2.51 MB 字体）残渣「降了」3.16 MB，比值 1.26×；语言对比（移掉 38.6 MB 字体）只「降了」2.24 MB，比值 0.058×。**不存在一致的传递函数，就说明这些差值是消融的重复性噪声。** 0.66 MB/会话落在同一条带子里，**不作为优化目标**（已否决，见 ADR-0007 推翻 4）。

**本轮未能测到的（无工具，不得当作论据）**：每进程 GPU 显存——WDDM 下 `nvidia-smi` 对本进程一律返回 `[N/A]`；堆分配归因——本机无 cargo-instruments / heaptrack / ETW。**「46.70 MB 是驱动」是「实测现象 + 源码排除法」的推断，不是直接测到的 GPU 分配记录。**

**对架构的影响（复述结论，不重开论证）**：本 ADR 的「按需会话」选择**继续成立且被强化**——既然残渣是驱动的、且第一次建窗就一次性付清，那么让不用的窗口**不启动会话**仍然是对的选择（把 46.70 MB 从「每天都付」变成「只在真的要开窗时付」）。**唯一被否决的替代方案是「用 Win32 自绘面板换掉 GL 上下文」**——它能省掉会话内的峰值与这份残渣，但 ADR-0006 已把它列为 Roadmap（两条渲染与输入路径的维护成本），v0.6.1 不动。

**两条给未来的取证纪律**（本轮踩出来的）：

- **任何内存采样必须等 ~12 秒落定。** 否则读到的是正在回落的中间值，斜率会被系统性高估。
- **工作集不是能还的东西，私有字节才是 commit charge。** 「裁剪工作集后掉了 92%」不能写成「内存泄漏修好了」。


## Considered Options

- 常驻 eframe（最初方案）：架构最简单，但 160~200 MB 常驻不可接受。
- 浮窗脱离 eframe 用 Win32 自绘（GDI/Direct2D）：内存可到 ~20 MB 且无会话切换，但要维护两套渲染与输入路径；列为 Roadmap，若驱动残留成为用户投诉点再做。
- wgpu 渲染器：不会更省，且显著增加二进制体积与编译时间。
