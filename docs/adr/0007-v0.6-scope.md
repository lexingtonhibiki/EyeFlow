# v0.6 范围裁决：做「双语 + 一次真正的体积削减 + 零风险微优化」，不做「极限优化」

## 背景

用户要求对 EyeFlow 做「极限优化升级」并提供中英双语。范围由用户拍板：双语覆盖 UI/用户可见文案 + README，CHANGELOG / ADR / 决策记录 / 内部注释保留中文。

总架构师产出 `docs/plan-v0.6.md`（705 行）作为设计输入，随后派出 A、B 两名独立审查者（互不知情、各自独立结论），本 ADR 是 C 方的最终判决。**凡与 `plan-v0.6.md` 冲突处，以本 ADR 为准。**

> **本文件是二次裁决后的版本。** 初版由主 agent 越权起草，其中若干条断言凭直觉写下、无证据支撑，甚至与同批的 ADR-0008 自相矛盾。二次裁决逐条复核，采纳的补上证据，推翻的写明错在哪。**唯一被完整推翻的裁决是判决二**，见文末「实施阶段被推翻的裁决」。

## 判决一：撤掉「18.8 MB 字体是 52 MB 残渣首嫌」这条主线 —— **采纳 A**

**依据：源码 + 仓库既有实测。**

架构师把每次 UI 会话无条件加载 `msyh.ttc`（实测 19,704,352 B = 18.79 MiB）称为最大单项、并归因为会话后不落回的残渣。A 方证伪，两条论据我都独立复核通过：

1. **仓库自己的记录已经归因驱动残留**：`docs/adr/0006-eframe-on-demand-ui-session.md:24` 的实测表写明「会话结束后空闲（驱动堆残留）~87 MB / ~60 MB」；`docs/lessons.md` 同结论。
2. **结构上字体不可能是不落回残渣的成因**（本轮复核）：字体数据是 `Arc<egui::FontData>`，挂在 **egui `Context`** 上——`set_fonts()` 只在 `src/app.rs:54`（`UiSession::new` 内）与 `src/app.rs:250`（`App::logic` 切语言时）被调用，而 `UiSession` 本身**不持有字体**（`app.rs:38-50` 的字段里没有 `FontDefinitions`/`FontData`）。全仓库无 `OnceLock`/`LazyLock`/`static FONTS` 之类的字体缓存（`grep -rn "OnceLock\|LazyLock" src/` 只在 `detector.rs:141-142` 命中键盘线程，与字体无关）。eframe 的 `run_and_return` 退出时 `Context` 被 drop ⇒ **字体随会话释放**。

**判决**：字体重新定位为**会话内峰值优化**，不是残渣修复。发布说明里**禁止**写「修好了内存残渣」——用户开一次设置窗再测会看到 55 MB 而非 0，会判定 v0.6 在骗人。正确表述是「回收了会话内峰值中的 18.6 MB」。

同时留下一条**未解决的量化问题**：单次会话后 55.14 MB、24.8 小时实例 77.41 MB，二者差 22 MB。若后者期间开过 N 次设置窗，则残渣按会话累积而非一次性稳态——**累积假说可解**（会话 TTL：最后一次关窗后保持 30~60 s），一次性驱动假说只能靠浮窗 Win32 自绘（ADR-0006 已列为 Roadmap）。**留待 v0.7，本轮不猜。**（依据：实测数字 + 推断，未做分解实验。）

## 判决二：英文模式字体用 Windows 自带 Segoe UI，不用 egui 内置字体 —— **采纳结论，推翻论据**

**依据：源码 + 实测。**

英文模式**不**退回 egui 内置字体、**改用 `segoeui.ttf`** 这条结论成立（A、B 双方独立得出，我复核成立）。但**初版 ADR 给出的论据有一条是错的**，必须更正：

| 初版写的 | 复核结果 |
|---|---|
| 「有真粗体」 | ❌ **假**。`segoeuib.ttf` 换不到任何字重，见判决二之二 |
| 「Ubuntu-Light 只有一个字重，所以英文界面显廉价」 | ⚠️ **事实成立但推不出结论**。epaint 0.36.1 的默认 Proportional 字体确实只有 `Ubuntu-Light` 一个字重（`epaint-0.36.1/src/text/fonts.rs:527-529`），但**中文模式加载 `msyh.ttc` 同样只有一个字重**（`from_owned` 硬编码 `index: 0` = Regular）——所以「没有粗体」不是英文模式独有的问题，换 Segoe UI 并不能解决它 |
| 「省下 18.6 / 18.8 MB ≈ 99%」 | ✅ 实测成立（仅在英文模式下成立） |
| 「ClearType hinting，是 Windows 自己用的字族」 | ✅ 成立（推断，无渲染实测） |
| 「Vista 起每台机器都有」 | ✅ 成立 |
| 「约 10 行代码、零构建期子集化漏字风险」 | ✅ 成立（`app.rs:550-553` 实为 2 个 `FontFile`，`build_font_defs` 共享） |

**判决二之一（结论，保留）**：英文模式字体链 = `segoeui.ttf` + `seguisym.ttf` 回退（`app.rs:550-553`），**不加 `segoeuib.ttf`**。

**判决二之二（部分推翻 —— 字重结论成立，`strong()` 的结论错了）**：`epaint 0.36.1` 与 `egui 0.36.1` 中 **`FontWeight` 出现 0 次**，`FontId` 只有 `{ size, family }`（`epaint-0.36.1/src/text/fonts.rs:27-34`，源码里明写 `// TODO(emilk): weight (bold), italics, …`）。因此：

- ~~`RichText::strong()` **在中英文下都是空操作**~~ —— **这句已被源码证伪，见「实施阶段被推翻的裁决 · 推翻 2」。`strong()` 改的是颜色不是字重，中英文下都生效。**「epaint 不支持字重」这半句仍然成立；
- 加 `segoeuib.ttf` 只会让它在 `segoeui.ttf` 缺某字符时充当第二道回退，**947 KB 换零收益**（这半句仍然成立）。

**连带裁决（不变）**：层次只能靠**字号 / 颜色 / 间距**建立。真正的字重阶梯需 epaint 上游支持 `FontWeight`，属 v0.7 议题，且**不得假设它会就绪**。**注意：「绕开字重」这个结论对，但「标题没有任何层级」是错的**——标题的**颜色**层级一直成立（纯白 vs 灰 140），被浪费的是**字号**那条通道。

## 判决三：i18n 用「build.rs 校验 + `tr(&str)` 函数」 —— **采纳 B**

**依据：源码（读实现 + 跑测试）。**

三方一致否决 Fluent / i18n-embed。A、B 在自研方案的**形态**上分歧：B 主张砍掉 `enum Key` + `tr!` 宏，改 `tr(&str)`，并把三个 `label()` 整个搬进 locale 表。

**判决：采 B 方形态。** 三条理由：

1. `label()` 若内部读 `AtomicU8` 语言状态，`config.rs` 的测试会变成**顺序相关**。搬进 locale 表后 `config.rs` / `core.rs` 保持纯数据。**复核通过**：`grep -n "fn label" src/config.rs` 在工作区**零命中**，枚举已只给 key。
2. 「编译期防 key 打字错」与 build.rs 的键集合校验**重复**；真正差异化、且所有 crate 都给不了的是**「缺任何语言的 key 直接让 `build.rs` `panic!` → 构建失败」**，必须保留。
3. 基础设施从约 200 行降到约 70 行。

**落地形态**（详见 [ADR-0008](0008-i18n-self-built-tr-layer.md)）：`locales/*.toml` → `build.rs` 用 `str::lines()` 解析（**不加 `toml` build-dependency**）→ `include!` 静态表 → `tr(key) -> &'static str`。

**默认语言**：`#[serde(default = "d_language")]` → 老 config.toml 走 serde default，行为与 v0.5.2 完全一致（`config.rs:235-236`）。`Config` 无 `deny_unknown_fields`，新字段被旧版读时静默忽略，降级也安全。

**`sanitized()` 缺陷（A 方案 9）已修复**（`config.rs:402-414`）：非法值（如手滑写成 `chinese`）**不静默切成英文并落盘**——能识别的值规范成 BCP-47 写法写回（`en_US` → `en-US`），**无法识别的原值原样保留**、界面上退到中文。A 方案 9 成立。

**三处翻译形态缺陷均已修复并各有测试兜底**：

- 复数（方案 B 5）：`runtime.rs:293` 已改调 `tr::tray_stats_line()`，把 `runtime.rs:245` 那个「一个 key 三个计数」拆成 `stats.done` / `stats.skipped` / `stats.postponed` 三个独立复数决策后拼装。
- ComboBox 长度预算（方案 B 6）：`FlowSensitivity` 的「低（30 秒内持续输入 > 40 键）」已拆成短名 + hover 说明。
- `human_duration` 的 `m == 0`（方案 B 7）：`ui.rs:787` 已有 `if minutes > 0` 分支，2 小时整点输出 `"2 h"` 而非 `"2 h 0 min"`；`tests/i18n_locales.rs` 的 `t12a_english_never_emits_a_zero_minute_form` 钉死这条。

## 判决四：主循环唤醒机制本轮不改 —— **采纳 B（推到 v0.7），并保留 A 的退路**

> ⚠️ **本条已于 2026-09-26 四次裁决被推翻（见「推翻 5」）。** 下面保留原文不改，作为「当初为什么这么判」的记录。

**依据：源码（双方读同一批 file:line，结论一致）。**

`tray-icon` 的托盘 HWND、`muda` 的 `TrackPopupMenu`、`global-hotkey` 的 `WM_HOTKEY` **全部走主线程消息队列**（`tray-icon-0.24.0/src/platform_impl/windows/mod.rs:83,102,545`；`muda-0.19.1/src/menu.rs:432`；`global-hotkey-0.8.0/src/platform_impl/windows/mod.rs:39,47,152`），所以架构师自标的「最高风险」不成立，`MsgWaitForMultipleObjectsEx` 技术上正确。

**但本轮不做**，理由采纳 B：i18n 已改遍 `runtime.rs` / `tray.rs` / `ui.rs` 每个调用点，再压上一个未经实战的循环重写，一次长跑要同时检验四个子系统，坏了无法二分定位。

**已做的退路**：`main.rs:39` 的 `LIGHT_LOOP_TICK` 由 200 ms 改为 **1 s**（`main.rs:153` 的 `sleep` 消费它），一行，零消息泵风险。`MsgWaitForMultipleObjectsEx` 改造推到 v0.7 单独做、单独提交、单独 soak。

200 ms 托盘延迟记入 Roadmap——**没有任何用户投诉过它，这个指标是架构师自己发明的**（方案 B 4 的观察成立）。

**`Core::tick` 自门控一并砍掉（采纳 A 方案 5）**：`core.rs:262-265` 已用 `dt = now - last_tick` 正确处理，5 Hz 调用是更精确不是错误；且门控会把预告浮窗（`heads_up_secs` 最小 5 s）的进入延迟从最坏 0.2 s 恶化到 1 s，**带来的问题比解决的问题大**。

## 判决五：真本体积靶子是 `ureq` 的 TLS 栈，不是 i18n —— **采纳 A 方案 10（最有价值的一条）**

**依据：源码 + 实测。**

A 方发现而架构师完全漏掉：`ureq = "3"` 用默认 features，`Cargo.lock` 里拖着 `rustls` + `ring` + `webpki-roots`，而 `update_check_enabled` 默认 `false`（`config.rs:210-212` + `config.rs:311`），`update.rs:1-9` 的模块注释自己写着「可选的更新检查（默认关闭）」。

**这是全文最大的讽刺点**：架构师拒绝 rust-i18n 的首要论据是「体积是这个项目的第一约束……用 5~8% 二进制换 6 KB 文案不成比例」——然后完全没检查自己 `Cargo.toml` 里一个 400+ KB 量级的**默认关闭**依赖。

**判决（已落地并实测）**：`ureq` 收成可选 cargo feature `update-check`，默认关（`Cargo.toml` 的 `[features]`）。**实测 10,224,640 → 9,085,440 B，净减 1,139,200 B（-11.14%）**——初版 ADR 写「`ring` 的确切字节贡献未测，实施时必须先实测」这条前置条件**已满足**。

**关于用户的唯一产品影响（初版留给用户拍板，现予裁决）**：

- 发行版二进制**失去在线更新检查**。`ui.rs:709-714` 的处理是：feature 关时**不显示那个永远勾不上的复选框**，改显示一行说明文案 `ui.update_check_absent`（「此构建未包含在线更新检查（体积优化）」/「This build has no online update check」）。**给用户一个按了没反应的开关比不给更糟**——这正是本裁决采纳的形态。
- 用户若已开 `update_check_enabled = true`：该字段仍在 config 里、能正常解析、不报错，只是没有检查动作发生。**这是可见且有说明的降级，不是静默行为改变。**
- **裁决：不需要问用户。** 理由三条：① 降级在界面上有明确说明，不是静默；② 该功能默认就是关的，绝大多数用户从未开过；③ 省下的 11.14% 是这个项目**第一条差异化卖点**（体积）。若用户日后要在线检查，`cargo build --release --features update-check` 即可，CI 已加该构建的 job 防止这条路悄悄烂掉。

**否决备选方案「改用 `windows` crate 的 `WinHttp`」**：能再省一点，但要多写一层 TLS/重定向/JSON 的胶水代码，而项目只有一人维护。收益（估 <100 KB，**未验证**）不抵维护成本。若将来体积还要再降，v0.7 再议。

## 判决六：panic hook 修 `MessageBoxW` —— **采纳 A 方案 11 的纠正 + 落地**

**依据：权威（std 文档）+ 源码。**

架构师把 `std::panic::set_hook` 判为「`panic = "abort"` 下的死代码」——**这是错的**：`panic = "abort"` 只取消 unwind，panic hook 由 panic runtime 在 abort 之前调用，照常运行。真正的问题是它只往日志文件写，**而托盘应用崩溃时用户什么都看不见**。

**判决（已落地）**：`main.rs:257-259` 的 hook 里加 `show_panic_message()`（`main.rs:272-`），用 `MessageBoxW`（`windows` crate 已在依赖里）。约 20 行，并对弹窗期间再 panic 的重入做了防护。护眼工具崩溃在用户眼里等于「这软件有问题」，没有第二次机会。

## 判决七：CI 门禁——fmt 全锁，clippy 限生产代码 —— **采纳 B（形式）+ A（不自欺）**

**依据：实测（`cargo clippy --bins -- -D warnings` 双工具链零警告）。**

`.github/workflows/ci.yml` 的 fmt 与 clippy 原先都是 `continue-on-error: true`，注释写「v0.2 重写期……稳定后可移除」，四轮迭代后仍在。

- `cargo fmt --check` → **阻塞**。零成本、不会因工具链差异误报，而一个永远不挡人的格式检查等于没有。
- `cargo clippy --bins -- -D warnings` → **阻塞**。今天生产代码已零警告，守住它不花钱。
  - ⚠️ **更正初版**：初版写的是 `--lib --bins`。**本项目是纯 bin crate、没有 lib target，`cargo clippy --lib --bins` 会直接报 "no library targets found" 而根本跑不起来**。实际用的是 `--bins`（`ci.yml` 内已注明）。
  - `--all-targets` 保持 **advisory**。理由：clippy 的 lint 集合每个 stable 版本都在变，`-D warnings` 之下一次例行工具链升级就红灯，唯一能修的人是作者，修法往往是加 `#[allow]`——**lint 工具一旦变成税就会催生 `#[allow]` 通胀，那比现在更糟**。
- **不加 GNU 矩阵**（采纳 B 方案 8）。`lessons.md:61` 那次事故的教训是「写显式断言」（用 `egui::vec2` 而非依赖推断），不是「矩阵翻倍」；为已根因消除的 bug 类别付永久 CI 成本是错配。minGW 容器自找麻烦、自托管 runner 是真实运维负担，而交付的是 Windows exe、MSVC 才是权威。**替代：本地推前跑一遍 GNU**（本机默认工具链就是 GNU，成本近零），已写进 `CONTRIBUTING.md`。
- **补 MSRV job**：`Cargo.toml` 声明 `rust-version = "1.95"` 但 CI 从未验证，装饰性的 MSRV 等于没有。MSRV 破坏是发版后用户立刻遇到的，优先级高于 GNU/MSVC 断言差异。
- **补 `--features update-check` 构建 job**：默认 feature 关掉了 TLS 栈，这个 job 保证那条路径不会悄悄烂掉（对应判决五）。
- 方案 A 8 称「原计划估 20~60 处清理，实测只有 6 处且全在测试代码」——**数量需更正为 8 处**（见实测基线），**「全在 `#[cfg(test)]` 内」的结论成立**，已逐行核对三个 `mod tests` 的起始行。

## 实施阶段被推翻的裁决

**这是本 ADR 二次裁决的核心产出。决策记录不记录被推翻的决策，等于决策记录只记录对的。**

### 推翻 1：ADR-0007 判决二的「有真粗体」与「加载 `segoeuib.ttf`」

- **初版裁决**：「英文模式加载 `segoeui.ttf`（约 700 KB）+ `segoeuib.ttf`（约 500 KB）……**有真粗体**」。
- **推翻依据（源码，级联复核）**：
  1. `epaint-0.36.1` 全文件 `FontWeight` 出现 **0 次**；`FontId` 只有 `{ size, family }`（`epaint-0.36.1/src/text/fonts.rs:27-34`，含 `// TODO(emilk): weight (bold), italics, …`）。
  2. **级联到 `egui-0.36.1`**：`FontWeight` 在 `egui-0.36.1/src/` 同样出现 **0 次**——不是 epaint 一层的问题，整条栈都不认识字重。
  3. `FontFamily` 的列表被当作**逐字符的 glyph 回退链**（`app.rs:583-584` 的注释描述正确），不是「常规体 + 粗体」这一对。
- **后果**：`segoeuib.ttf` 只会作为 `segoeui.ttf` 缺字时的第二道回退，**947 KB 换零收益**。已从 `EN_FONTS` 移除。
- **代码改动裁定：保留，不回退。** `src/app.rs` 的 `EN_FONTS` 移除 `segoeuib.ttf` 这处改动**成立**——它由上三条源码证据直接支持，且 `app.rs:536-549` 的注释已把结论写清楚。
- **级联修正**：初版判决「theme.rs / 6 级字重阶梯推 v0.7，理由是地基不存在」措辞暗示地基将来会就绪。**实际是 epaint 上游不支持 `FontWeight`，地基在可预见的未来不会就绪**——v0.7 的排版体系必须**完全绕开字重**。

### 推翻 2：「`RichText::strong()` 在中英文下都是空操作」 —— **源码证伪，它改的是颜色**

- **被推翻的裁决**（本 ADR 判决二之二，**并已扩散进 `src/app.rs:544` 与 ADR-0008 的生产注释**）：「`RichText::strong()` 在中英文下都是空操作……`ui.rs` 的卡片标题、预告浮窗标题一直没在加粗，只是没人注意。」
- **推翻依据（源码，本轮 C 方逐行复核）**：
  1. `egui-0.36.1/src/widget_text.rs:252`：`pub fn strong()` 置 `self.strong = true`。
  2. `egui-0.36.1/src/widget_text.rs:484-485`：`} else if self.strong { Some(visuals.strong_text_color()) }` —— **它参与的是取色**。
  3. `egui-0.36.1/src/style.rs:1146-1148`：`strong_text_color() = self.widgets.active.text_color()`。
  4. `egui-0.36.1/src/style.rs:1710`（dark）`active.fg_stroke = Stroke::new(2.0, Color32::WHITE)`；`:1686`（dark）`noninteractive.fg_stroke = Stroke::new(1.0, Color32::from_gray(140))`。
  5. **结论**：标题实际渲染为**纯白 255**，正文为**灰 140**——**亮度差 82%**。「标题层级早就成立了」这句话是错的。
- **为什么原裁决会错**：只查了 `epaint` 的 `FontId` 有没有 `FontWeight` 字段，**没查 `strong()` 这个 builder 方法到底改什么**。字重确实没有，颜色确实有，两件事被合并成了一句「空操作」。**「上游没有 X 字段」推不出「用了 X 的那个 API 是空操作」**——这是本 ADR 要记住的教训形状。
- **后果（改动代码，不是只改文档）**：`ui.rs:149` 的卡片标题是 `.strong().size(14.0)`，而项目自己在 `app.rs:319`（休息面板标题）与 `app.rs:378`（欢迎回来闪屏）用的是 `.size(17.0).strong()`。**设置窗是全项目唯一的异类。** 把 `ui.rs:149` 的 14.0 提到 17.0 的性质因此变了：**不是「救一个看不见的标题」，是「给一条已经成立的标题补上第二条通道（字号），并消除与 `app.rs:319/378` 的内部不一致」**。
- **同时必须更正的两处生产注释**（否则错误断言留在代码里，下一个读注释的人会拿它当依据）：
  - `src/app.rs:544`「`RichText::strong()` 在中英文下**都是空操作**——包括 v0.5.2 的中文界面。」
  - `docs/adr/0008-i18n-self-built-tr-layer.md:97`（见该 ADR 的同款修订）。
- **本 ADR 明确不翻回的半句**：「epaint 0.36.1 不支持 `FontWeight`」**仍然成立**（推翻 1 的三条源码证据未受影响）。字重阶梯仍是 v0.7 议题。

### 推翻 3：「给 `max_texture_side` 设上限以压住字体图集内存」 —— **源码证伪，且方向是反的**

- **被推翻的裁决**（v0.6.1 内存分析员提出，A 方复核否决）：把 `FontOptions::max_texture_side` 压到 2048，理由是「epaint 会把每个字体的全部字形烘进一张 16 KiB 见方的纹理」。
- **推翻依据（源码）**：`epaint-0.36.1/src/text/fonts.rs:981` 是 `let texture_width = options.max_texture_side.at_most(16 * 1024);` —— **egui 自己已经把上限夹在 16 KiB**，外部传再小的值不会进一步限制；真正决定图集尺寸的是 `initial_height = 32` 起步、按需增长。
- **实测**：本机实际图集为 **2~8 MB**，不是理论上限的 1 GiB 量级。
- **为什么方向是反的**：图集越小，切图时触发的**整图 clone 次数越多**。压到 2048 净效果为**负**。
- **代码改动裁定**：本轮**没有任何 `max_texture_side` 调用点被写入过**（`grep -rn "max_texture_side" src/` 零命中），所以没有代码要回退。记在此处是为了**堵住下一轮重新提起的路**。

### 推翻 4：「~1 MB/会话 的常驻内存漂移是 v0.6.1 的靶子」 —— **A 方的数据一致性检验否决**

- **被推翻的裁决**（v0.6.1 内存分析员提出）：把 20 次开关设置窗测出的 `0.66 MB/会话` 斜率定为 v0.6.1 的优化目标。
- **推翻依据（实测数据自洽性检验，A 方提出、C 方采信）**：两次「移掉字体 → 看残渣降多少」的消融，比值相差 **22 倍**，不存在一致的传递函数：
  | 消融 | 移掉的字体 | 残渣变化 | 比值 |
  |---|---|---|---|
  | 去掉 `seguisym` | 2.51 MB | −3.16 MB | **1.26×** |
  | 中文链 vs 英文链 | 38.6 MB | −2.24 MB | **0.058×** |
  - 若存在真实传递函数，这两个比值必须同量级。**22 倍的差说明 ±3 MB 的残渣差是消融的重复性噪声，不是被解释掉的量**。`0.66 MB/会话` 落在同一条噪声带内。
- **同轮的独立佐证**：`SetProcessWorkingSetSize(-1,-1)` 把工作集从 38.19 MB 压到 3.22 MB（−92%），而**私有字节几乎不动（60.21 → 60.21）**。工作集不是用户态能回收的东西，**私有字节才是 commit charge**——所以「工作集掉了」从来不是「内存泄漏被修好了」的证据。
- **代码分析方自己提出的竞争假说也被自己的同事证伪**：分析员曾提出「42.12 MiB 字体链 + 8.4 MiB 图集 = 50.5 MB ≈ 52 MB 残渣」。**这与实测直接冲突**——把 38.6 MB 字体整个换掉，残渣只动了 2.24 MB（3.4%）。**这条假说被证伪后，「字体现在常驻 42 MB」的直觉也就跟着失效了。**
- **代码改动裁定**：本轮**不追 1 MB/会话**。正确姿势是 A 方的替代方案（60 次三组对照，目标从「确认」改成「排除」）——见 ADR-0006 的实测附录。

### 推翻 5：「`MsgWaitForMultipleObjectsEx` 推到 v0.7」—— **推迟的理由已失效，实测证明它是本项目唯一的大额可动项**

- **被推翻的裁决**（本 ADR 判决四）：主循环唤醒机制本轮不改，`LIGHT_LOOP_TICK` 留在 1 s，`MsgWaitForMultipleObjectsEx` 改造推到 v0.7 单独做。
- **为什么这次必须重开**（用户诉求：「从托盘点击到显示窗口会有短暂的黑屏、加载组件，这部分可以再提速不」）。分段实测（zh，n≥3，中位数）显示轻量循环这一段**均匀吃掉 0~1 s 的全部**：

  | 段 | 实测 |
  |---|---|
  | **托盘点击 → `rt.step` 响应** | **p50 ≈ 539 ms / p90 ≈ 900 ms / 最坏 1000 ms** |
  | `OpenSettings` → step 返回 | 1.5 ms（`SettingsState::new` 克隆整份 Config，可忽略） |
  | `run_native` 入口 → `CreationContext`（winit 事件循环 + 根窗口 + WGL + glow + 着色器编译） | **690~803 ms**（p50 ≈ 750，全样本 503~847） |
  | 字体 `fs::read`（zh 19.7 MB / en 3.4 MB） | 17 ms / 3 ms（冷缓存首跑 +90 ms） |
  | 窗口可见 → 设置窗 pass 开始 | 89 ms（NVIDIA 驱动的 per-surface 上下文切换，第二帧同段只要 0.32 ms） |
  | 布局 + tessellate + 上屏 | 27 + 33 ms |
  | **合计 点击 → 第一个有内容的帧** | **1099~1723 ms** |

- **判决四自己已经让步的那一半，不该继续欠着**。判决四原文写明「`MsgWaitForMultipleObjectsEx` **技术上正确**」——技术正确性从来不是推迟的理由。原文给出的推迟理由只有一条：「**i18n 已改遍 `runtime.rs` / `tray.rs` / `ui.rs` 每个调用点，再压上一个未经实战的循环重写，一次长跑要同时检验四个子系统，坏了无法二分定位**」。**这是一条排期理由，不是架构或正确性理由，而它的前提条件已经完全消失**：v0.6.1 已提交（`ae87b79`），84 个测试全绿，i18n 已落地。**拒绝履行一条已经到期的技术正确性让步，代价是一个用户每次点托盘都要等半秒到一秒。**
- **推翻依据（实测，非推断）**：上表第一行。`LIGHT_LOOP_TICK = 1 s`（`main.rs:39`）由 `main.rs:153` 的 `std::thread::sleep` 原样消费，中位数 539 ms 与 1000 ms 的均匀分布**就是这一行 sleep 的分布函数**，没有别的解释。
- **另一条猜测已被证伪，堵住「换更快的 pump」的回头路**：曾怀疑「`pump_win32_messages()` 的 `PeekMessageW` 泵推迟了消息分发」。**实测 `pump_done → 点击被检测 = 0.017 ms`**——`muda` 的 `MenuEvent::send` 是同线程同步投递，那个 `WM_COMMAND` 由 `TrackPopupMenu` 在模态循环里同步发给隐藏窗口，发生在 `pump_win32_messages()`（`main.rs:190`）的 `DispatchMessageW` 内部，而 `tray.poll()` 就在 pump 之后同一个 `step()` 里。**换 pump 写法一分都省不下。**
- **代码改动裁定**：**做，但保持判决四的退路可用**。`MsgWaitForMultipleObjectsEx` 属 `windows::Win32::System::Threading`，`Cargo.toml` 的该 feature **已启用**（`Win32_System_Threading`），**Cargo.toml 不需要改**。
  - **⚠️ 实施阶段修正：本裁定里「空闲 CPU 保持 0.177%」这句话是错的，实测证明替换有 CPU 代价。** 主 agent 的**同会话 4 轮交替 A/B**（每轮空闲 3 min，为抵消机器状态漂移）：`MsgWaitForMultipleObjectsEx` 均值 **0.777%**（0.712 / 0.990 / 0.668 / 0.738），`std::thread::sleep(1s)` 均值 **0.534%**（0.408 / 0.877 / 0.469 / 0.382），**差 +0.243 个百分点，四轮里每一轮都是 `MsgWait` 更高**。折合约合每天多耗 3.5 分钟 CPU。**裁定仍为「做」**——用 3.5 分钟/天换点击响应 p50 593 ms → 十几毫秒（37 倍）划算——**但不能再按「零 CPU 代价」对外描述**。
  - **本裁定给的唤醒掩码 `MWAIT_INPUT_AVAILABLE | MWAIT_ALL_COMPLETED` 也是错的**，实现阶段已推翻：windows 0.62 不导出 `MWAIT_*` 常量，而 `MWAIT_INPUT_AVAILABLE` 对应的那一位只在真有键鼠输入时置位，别的线程 `PostMessage` 来的托盘 / 热键 / `WM_COMMAND` 只置 `QS_POSTMESSAGE (0x0008)`，两者与运算为 0，**永远等不到**（实测 p50 仍是 609 ms，与 `sleep(1s)` 一模一样）。正确掩码是 `QS_ALLINPUT (0x04FF)`。详见 `src/main.rs:wait_for_input_or_fallback` 的注释。
  - 本文件上文表格里 `0.177%` 那一列**今天在本机复现不出来**（`sleep` 对照组实测 0.534%），来源条件已无从考证。所有 CPU 结论以本次同会话 A/B 为准。
- **同批否决的两条**（理由与推翻 3/4 同源：都不是「大头」）：
  - **退回 200 ms tick（方案 A'）**：**否决**。它只把中位数从 539 ms 砍到 ~100 ms，**仍然慢**，而空闲 CPU 翻 2.7 倍。判决四当初的 CPU 数字依然成立。
  - **延迟显示设置窗以消除 121 ms 黑屏（方案 B）**：**本轮不做**。纯 egui 形态（`ViewportBuilder::with_visible(false)` + 下一帧 `ViewportCommand::Visible(true)`）是**净亏损 ~530 ms**：`ViewportCommand` 进的是 `Context` 命令队列，`end_pass` 才进 output，**最早只能下一帧生效**，而下一帧最坏要等 `app.rs:267` 的 `request_repaint_after(500 ms)`（实测额外 654~752 ms）。改用同帧 Win32 `ShowWindow(SW_SHOWNOACTIVATE)` 能把黑屏压到 308~461 ms，**但那一轮的端到端可见时刻没有闭环**——活体枚举同时看到一个 1440×740 不可见窗口和一个 718×827 可见窗口，探针用标题匹配分不清是哪个 hwnd 变了可见。**机制已被源码证实（`eframe-0.36.1/src/native/glow_integration.rs:208` 给根窗口 `.with_visible(false)`，`src/native/epi_integration.rs:380-386` 首帧后才 `set_visible(true)`；子视口走 `src/native/glow_integration.rs:1571` 的 `render_immediate_viewport` → `egui-winit-0.36.1/src/lib.rs:2051` 的 `.with_visible(visible.unwrap_or(true))`，没有这层保护），但落地前必须先做一次把两个 hwnd 用 `GetWindowThreadProcessId` + 矩形区分开的复核。** 121 ms 占 1100~1700 ms 总时延的 7~11%，**排在 500/900 ms 后面**。
  - **构建期字体子集化（方案 C）**：**否决，且重申 ADR-0008 的否决**。收益 12~15 ms I/O，占总时延约 1%；代价是把「加一条文案 = 改 2 个 locale 文件」变成「再加一步重新生成字体」，并给 CI 引入一个 Python/fontTools 依赖（`.github/workflows/release.yml` 现在只装 NSIS）。**漏字在构建期嵌入后运行时无法补救**这条否决理由不但仍然成立，在 v0.6.1 把中文字体链砍到 22.2 MB、locale 键涨到 178 之后**更成立**。

### 本节新增的取证纪律（本轮付出代价换来的）

1. **「上游没有 X 字段」推不出「用了 X 的 API 是空操作」。** 推翻 2 的直接成因。查一个 API 的行为要读它自己的实现，不是读它依赖的数据结构。
2. **一个「省内存」建议必须先问「省的是哪一块」。** 推翻 3 与推翻 4 是同一种错误的两个版本：都在优化一个**从未被测量证明是大头**的量。
3. **两次消融的比值差一个数量级，就该先怀疑噪声，而不是先建立传递函数。** 数据自相矛盾时，最省事的解释通常是对的。
4. **本仓库的字体/字形测试与生产代码是解耦的**（`tests/i18n_glyphs.rs:25` 的 `ZH_FONTS` 是一份**手抄的字面量**，不从 `src/app.rs` 解析；T11d 用 `src.contains("msyh.ttc")` 扫源码全文，注释里出现字符串就算过）。**改字体链时测试不会替你抓住回归**，必须手工加断言。见 ADR-0008 的修订。
5. **「推迟」必须写清是排期理由还是架构理由，并且排期理由要写明它的到期条件。** 推翻 5 的直接成因：判决四把一条**技术上已确认正确**的改造推迟，理由只有「这轮 i18n 改动太多、坏了无法二分定位」——那是排期，不是架构。排期条件一旦消失（i18n 已提交、84 测试全绿），这条推迟就自动失效，**继续挂着它等于让用户每次点托盘多等半秒**。一份决策记录如果只写「推 v0.7」而不写「什么条件下重开」，它就会变成一条没人负责的欠账。

## v0.6.1 追加裁决：内存取证 + 审美复审（2026-09-26）

### 内存侧的终局结论（一句话）

**没有泄漏。46.70 MB（占残渣 71%）是 GL 上下文与 NVIDIA 驱动的一次性初始化 commit，用户态拿不回；本轮唯一值得做的内存改动是砍掉两个对字形覆盖贡献为零的字体文件，它降的是**会话内峰值**而不是常驻。**

**关于「专攻内存」这个原始要求的诚实结算**：本轮内存侧能交付的**可见**收益只有一项（会话内峰值，且用户只在「设置窗开着的那几秒」看得见任务管理器）。**常驻内存一行代码都改不动**——那是驱动的 commit。所以本轮 CHANGELOG **一个字都不许提「降低常驻内存」**（A 方明确要求，C 方采信并升级为硬约束）：用户看不到任何变化，在 CHANGELOG 里承诺一个他量不到的数字，比不承诺更糟。

### 排除实验（A 方的 60 次方案，**采纳但改判据**）

- **原设计**：300 次确认「1 MB/会话」是真的。**改**：300 → **3 组 × 20 次 ≈ 30 分钟**，目的从「确认」改成「**排除**」。
  - A 组：每会话走最长路径；B 组：每会话开 1 秒就关；C 组：en-US 走 A 组路径。
  - **判别规则**：A 组斜率 ≫ B 组 → 是工作量驱动的 churn（**可修**，进 v0.7）；三组一致 → 是驱动 per-context（**不可修**，写进 ADR-0006 的已知限制后结案）。
- **先跑两个零成本筛选**（各 30 秒 / 30 分钟）：
  1. **句柄数 + 线程数 + 模块数**跨会话是否恒定 —— 若恒定，则「每会话泄漏」在 OS 可见层面被排除。
  2. **会话结束后立刻采一次 vs 等 30 秒后再采** —— 残渣落定需 ~12 秒（实测），差值若归零则斜率是采样时机伪影。
- **与本轮裁决的关系**：这是**唯一**一件「做完可能把 v0.7 的排期改掉」的实验，因此**做**；但它**不阻塞** v0.6.1 发布。

## 决策的已知代价（诚实记账）

1. **i18n 是长期承诺，不是一次性成本。** v0.6 之后每次改文案要改两个文件。原计划用「迁移成本 = 重写 `locales/*.toml`，代码调用点零改动」自安，但这只覆盖**架构迁移**，不覆盖**日常维护**。本 ADR 认为这个成本可接受——它就是双语项目本身。
2. **否决 rust-i18n 的理由强度低于原计划所述。** 该项目只有一人维护，翻译者就是作者本人，rust-i18n 的头号缺点（翻译要改 Rust 文件）在这里**不存在**；真正的理由只有体积。**且全程无网络，无法验证 rust-i18n 当前版本是否仍依赖已被 dtolnay 归档的 `serde_yaml`**——原计划的这条依据未被任何一方证实，**标记为「未验证」**。结论仍是否决，但**理由只有体积一条成立**。
3. **52 MB 残渣的成分本轮未分解。** 全部为推理 + 项目已有实测记录的交叉验证，未经本机测量。
4. **`rust-i18n` / `i18n-embed-fl` 是否真实存在且当前依赖树如何：全程无网络，未验证。**
5. **架构师的「现状审计」表格行号有系统性错误**：全角空格实为 14 处（列了 17 个行号，其中 7 个不存在、6 处实际存在的漏列）；状态色「在 `ui.rs:167-169` 与 `app.rs:167-169` 各写一遍」**不成立**——`app.rs` 里**没有任何** `rgb(70,170,100)`（实测 `grep -rn "70, *170, *100" src/` 只命中 `ui.rs:216,732,769`），真实重复是 `ui.rs` 内的 10 处 `from_rgb` 字面量、3 个色值（`config.rs:575` 之外的生产代码里 `ui.rs:216-218` 定义、其余 7 处重复）。**结论不受影响，但所有「量化」列的可信度要打折**——这正是设立 A/B 独立审查的价值。
6. ~~**判决八的两处新漂移尚未修复**（`spec.md` 的 `segoeuib` 与 N5 体积），见实施清单「必须做」。~~ ✅ **已关闭（2026-09-26）**：两处均已修（见判决八）。**本条在写下时是真缺口，不要因为「已关闭」就以为它从来不是问题**——`spec.md` 的 `segoeuib` 是被 ADR-0008 判决二推翻的旧预期，N5 体积是 `ureq` 可选化之后没跟上的记账漂移，两者的成因不同：一个是预期被推翻没同步，一个是实测变了没记账。

## v0.6.1 追加裁决的 Sources（本轮 C 方亲自复核）

- **字形覆盖（实测，fontTools 直读系统字体 cmap）**——推翻「`msyhl` / `simhei` 是必要的 glyph 兜底」：
  - 现有 `locales/*.toml` 全部去重字符 **508** 个（en-US 85 + zh-CN 494，去 tab）。
  - **「需要 `msyhl` 或 `simhei` 才能画出来」的字符数 = 0**。即 `(msyhl ∪ simhei) − (msyh ∪ seguisym) ∩ 文案字符 = ∅`。
