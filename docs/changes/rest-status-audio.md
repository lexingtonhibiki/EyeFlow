# Rest status and start-cue consistency

## Problem and scope

The status tab offered no direct rest-duration editing. The Reminder tab's short-duration slider exposed 10–90 seconds although configuration accepts 10–600 seconds. Manual and automatic break starts treated the existing start-cue option differently: automatic HeadsUp → Break never emitted the cue. The reported screenshot also has both start and heads-up cues explicitly disabled; that configuration is intentionally silent on those events, not proof of an audio-device fault.

## Decisions

- Reuse existing persisted fields, defaults and save action. No schema migration, new dependency or silent enablement.
- Status shows next reminder, state and statistics, editable short seconds (10–600) and long minutes (1–60), the long-break enabled state and a route to full reminder settings. Explain that edits affect the next break.
- Preserve fractional-minute configurations on rendering; only user edits normalize to minutes.
- Existing `start_cue_enabled` governs both manual and automatic starts; explicit false remains false. Master sound remains a runtime gate. Heads-up and completion events retain their separate behavior.
- A repeated manual action during Break returns false and must not play another start cue or reset the break deadline.
- No changes to audio-device selection, retry behavior, quiet hours, or prior-session logs.

## Acceptance mapping

| Requirement | Evidence |
|---|---|
| Automatic start emits exactly one cue when enabled | `automatic_break_start_cue_follows_start_cue_enabled` (fails against the old transition, passes with fix) |
| Short/long start events independent of heads-up toggle | `start_sound_is_independent_of_heads_up_sound_for_both_break_lengths` |
| Repeated manual action rejected | `start_break_now_returns_false_when_already_in_break` and runtime boolean gate |
| Completion cue independent of start toggle | `disabled_start_cue_does_not_disable_completion_cue` |
| Viewing status does not save/mutate preferences | `status_render_preserves_durations_and_explicit_sound_choices` |
| Cross-tab bounds and non-whole-minute values preserved | `rest_durations_survive_reminder_status_round_trip` with 60/120/125/1800/1860/3600 seconds |
| Active deadline unchanged after duration edit | `duration_edit_applies_to_next_break_not_current_deadline` |
| Bilingual UI | locale key parity enforced by build script; layout tests |
| Audible Windows output | Requires real Windows device verification; dispatch/unit tests are not an acoustic test |

## Workflow provenance

Implementation proposals were generated by OpenDesign `deepseek-v4.1-flash` in separate audio and UI write scopes, integrated and independently checked by Codex. This is AI-generated/AI-reviewed work, not a claim of human review. First audio tests had a deadline error; first UI response exhausted its output budget, and the retry referenced a nonexistent field. These failures were retained and corrected rather than counted as successful deliveries. No remote commit, PR or release is authorized by this local patch.

Independent review also found that the old Reminder slider still clamped long breaks to 3–30 minutes. A real egui no-input round-trip test reproduced 60 seconds becoming 180. Both pages now use the same 1–60 minute bounds, with no writeback on ordinary rendering.

Final local validation: 212 test cases passed across library, binary and integration suites; 9 explicitly ignored upstream tests remain ignored. `cargo clippy --bins -- -D warnings`, `cargo fmt --check`, and `git diff --check` passed. A workspace-only toolchain and native development sysroot were used. GUI capture was attempted but Xvfb could not open sockets in this sandbox; no Windows speaker or screenshot approval is claimed. The final cross-page fix was implemented by Codex after the DS endpoint returned HTTP 503 with no usage receipt.


## Authorized Windows acceptance follow-up

The owner approved publishing this candidate and an acceptance workflow to a new
isolated test branch, without merging or releasing. This supersedes the local-only
publication note above for this test branch only.

The added Windows workflow first checks the default production binary with the
existing native tray/window/quit smoke. A separately built `desktop-smoke`
executable logs read-only widget geometry and loaded UI state only when launched
with `--smoke-stdin`. Python uses real mouse/keyboard input to edit durations,
verifies real page transitions and loaded state after a new process starts, and
captures screenshots. It does not mutate configuration through the observation
channel. Every process gets archived logs. Configuration and sound are isolated
from the owner's desktop. Sound output is deliberately disabled and unverified.

The prepared cases cover preserving 125 seconds when viewing pages/restarting,
then native widget edits to 1 and 60 long-break minutes and 599/600 short-break
seconds, disk persistence, status/reminder page round-trips and process restart.
These are prepared assertions, not a claim that Windows execution has passed.

Local restoration on 2026-11-13: exact original patch restored from its saved
artifact and applied to unchanged dev/main 6b0be65. Shared-core tests passed
(87 test cases), Rust format, Python compile and diff whitespace checks passed.
Windows GUI, speaker output and Windows GNU execution still require their
respective environments; cross-compilation is not native execution.

The current acceptance-instrumented code additionally passed Rust 1.95 GNU
Windows cross-target checking with `--no-default-features --features desktop-smoke`.
This did not link or run a Windows executable and excludes update-check; the
resource compiler was unavailable and emitted the existing warning. It is not a
substitute for the CONTRIBUTING native GNU test or the pending Windows GUI run.
